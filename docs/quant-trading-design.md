# 缠论量化交易设计（欧易 / MySQL）

开发分支：`codex/okx-quant-trading`。

## 1. 目标和当前交付

以现有缠论工具为基础，最终形成“历史验证 → 欧易模拟盘 → 小资金实盘”的系统。
部署数据库采用 **MySQL 8.0.16+ / InnoDB / utf8mb4**（需要 CHECK 约束支持），
推荐在维护中的 MySQL 8.4 环境验证。Redis 第一阶段不引入。

本次实现是研究阶段的可运行代码，不是可上线的自动交易机器人：

| 内容 | 状态 |
|---|---|
| 独立量化模块，复用 `chan.analyze`，不改缠论算法参数 | 已实现 |
| 逐根收盘回放、4H / 15m 时间对齐、输入校验 | 已实现 |
| 信号观察、锁定时间、每根决策及过滤原因持久化 | 已实现 |
| B2/B3/S2/S3 锁定、顺势、结构位、扣费后盈亏比过滤 | 已实现 |
| Decimal 线性合约风险仓位计算 | 已实现，独立函数，尚未接账户或持仓引擎 |

## 2. 模块与运行边界

```text
当前：历史 JSON → 输入校验 → 按收盘时间推进 → 缠论快照 → 策略过滤
                                                    ↓
                                       MySQL / SQLite → 回放报告

后续：欧易行情 → 后台行情服务 → 同一策略过滤 → 账户风控 → 订单执行器 → 欧易
                     ↓                 ↓            ↑          ↓
                  历史行情库       信号与决策库       对账 ← 订单/持仓更新
                                                    ↓
                                             主界面状态与告警
```

Flask 继续负责展示和查询。新增后台进程负责行情与交易，关闭网页不影响它。
交易进程只允许一个有效主实例；不能用 Flask 请求处理器或定时页面刷新驱动下单。

## 3. 策略 V1 的确定性规则

范围限定 BTC-USDT-SWAP、ETH-USDT-SWAP，4H 定方向、15m 找买卖点。
这是一套待研究假设，并非已有统计优势的策略。

1. 大级别用最新已收盘 4H 的缠论结构判断方向；中性不入场。
2. 从小级别最近两个已确认笔端点范围内选最新 B2/B3/S2/S3。
   同时出现多个类型时按时间、类型确定顺序；选中信号不合格时不回退捡旧信号。
3. 必须 `locked is True`；字段缺失也禁止。评分只记录，不解释为胜率。
4. 信号极值需靠近 4H 中枢 ZG/ZD 或最近上下笔端点。EMA 不参与自动入场与目标。
   验证容差沿用现有联动页：近 20 根大级别 `(high-low)/close` 均值 × 0.6。
5. 止损固定采用该信号极值外 0.2% 缓冲，现价已越过则失效。
   这是量化 V1 的明确选择，不采纳联动页“关键位或信号位”的动态止损选择。
6. 目标为顺方向最近的结构位；无目标则观望。
7. 用收盘参考价加不利开仓滑点，止盈/止损也估算不利滑点和双边手续费，
   净盈亏比未达到 2 则观望。默认单边费率及滑点各 0.0005，仅用于研究假设。
8. 同一回放中同一信号最多输出一次候选。交易执行阶段另有持久化订单去重，
   研究候选去重不能代替实盘去重。

保留新笔 ≥5 根处理后 K、MACD HIST=2×(DIF−DEA)、面积比 <0.7、中枢最多延伸 9 段。
不重新引入已移除功能。原单周期和多周期网页继续保留原有展示口径。

## 4. 时间、重绘与回测可信度

内部时间统一为 **UTC 整数毫秒**。OKX K 线 `ts` 是开盘时间，
15m 的收盘事件是 `ts + 900000`；4H 是 `ts + 14400000`。

每个 15m 收盘事件只传入当时已经收盘的小级别前缀，以及收盘时间 ≤ 该事件的 4H 前缀。
大小级别同时收盘时，研究模型假设两份收盘数据均已到达；未来实时服务必须等两份数据实际到达，
记录接收时间，超过容忍时延则跳过，不以理论收盘时间冒充实际可交易时间。

两级别分别至少预热 40 / 80 根，每次最多计算最近 600 根；窗口截断策略记录在配置中。
输入必须升序、无重复、无缺口；仅可包含一根未收盘尾 K，该尾 K 排除。
大级别数据如果提前结束，拒绝整次回放，避免持续使用过期方向。

报告时间含义：

| 字段 | 含义 |
|---|---|
| `extreme_at` | 图上信号极值所属 K 线的开盘时间，不是可入场时刻 |
| `first_observed_at` | 回放开始评估后第一次看到信号的收盘事件时间 |
| `first_locked_observed_at` | 第一次观察到该信号已锁定；未观察到则为空 |
| `first_observation_left_censored` | 首次评估时信号已存在，无法知道它更早何时出现 |
| `observed_at` / `eligible_after` | 本次决策时刻；未来订单只能在此之后执行 |

不是把最终图上的历史点向前填入回测。前缀一致性测试会将一段历史单独回放，
再追加未来数据回放，比较两次在相同历史时刻的决策是否一致。
信号以 `inst + bar + type + 极值时间` 做稳定哈希，不以会随窗口左移的 `k_idx` 去重。
信号移到新极值时形成新身份；旧快照保留，允许研究撤回和重绘。

完整收益回测后续需补齐：

- 以信号可用后的下一根开盘或更细粒度行情执行，加入网络及数据接收延迟；
- 入场再次校验实际价格、止损是否失效、净盈亏比、信号过期；
- 限价单排队、未成交、部分成交及撤单，不默认触价即全成；
- 同根 K 线同时触及止盈止损时，用更小周期还原或保守按止损先触发；
- 跳空止损以首个可成交价计损失，不能固定亏损恰好等于风险预算；
- 按真实费率和结算时刻计手续费、历史资金费；
- 第一版固定结构目标全部退出，加入明确最大持仓期限，结束数据时按市值标记未平仓；
- 参数选择与样本外测试分离，按趋势/震荡/高波动拆分结果，保留交易明细和成本敏感性分析。

## 5. 数据库设计

### 已实现研究表

| 表 | 主键与内容 |
|---|---|
| `quant_schema_migrations` | 迁移文件名；校验和防止已应用迁移被覆盖修改 |
| `quant_runs` | `run_id`；运行状态、开始/结束时间、配置、源码哈希、数据哈希、摘要 |
| `quant_candles` | `(run_id, inst, bar, open_ts)`；该次回放的标准化收盘 K 快照 |
| `quant_signal_observations` | `(run_id, signal_key, observed_at)`；极值时间、当时锁定状态及完整信号 |
| `quant_evaluations` | `(run_id, observed_at)`；候选/观望、机器可读原因、价位与时间水位 |

研究输入按回放保存，便于复现；数据规模变大后增加不可变数据集表，运行只引用数据集版本，
避免多次回测重复保存完整行情。第一版每次回放只处理一个品种，组合回测需要共享账户时钟。

快照列使用 LONGTEXT 保存严格 JSON（禁止 NaN），便于 SQLite 与 MySQL 共用研究接口。
主键使用有长度的 VARCHAR，时间使用 BIGINT；MySQL 显式指定 InnoDB 与 utf8mb4_bin。
价格计算沿用现有分析代码的浮点值，风险数量计算使用 Decimal；未来订单金额字段使用
`DECIMAL(38,18)`，不能把研究 JSON 浮点直接用作欧易下单金额。

每个收盘事件的信号与决策在一个事务提交。异常时回滚该事件并将运行标记 failed。
进程被强制终止可能保留 running，当前不自动恢复该回放；重新回放会生成新 run_id。

迁移取得当前数据库专用 GET_LOCK；SQLite 用 BEGIN IMMEDIATE。
**MySQL DDL 会隐式提交，不能声称整套建表可事务回滚。**001 仅用可重试建表语句，
全部成功后才记迁移版本；失败可重跑。后续 ALTER 类迁移必须单独设计可重入步骤和恢复方式。
必须使用专用数据库，禁止手工预建同名但结构不同的表。[MySQL 事务说明](https://dev.mysql.com/doc/refman/8.0/en/innodb-autocommit-commit-rollback.html)

## 6. 风险预算和张数

初始研究风控建议：单笔风险 0.5%、组合未平仓风险 1%、最多同时两笔，
日亏 3% / 周亏 6% 暂停新增订单。日/周按 UTC 日界和周一计算，权益包含未实现盈亏及费用；
充值提现需调整基准，触发后不能因浮盈回升自动解除。熔断状态需要人工复核后解锁。
这些账户级熔断是下一阶段功能，当前 `risk.py` 不假装已经执行。

已实现风险函数：

```text
本单风险预算 = min(权益×单笔风险比例, 权益×组合风险比例－已有风险)
每张预计亏损 = 每张基础币数量×(不利止损成交价差＋开平手续费)
张数 = floor_to_lot(min(
    本单风险预算/每张预计亏损,
    可用保证金/每张保证金与费用预留,
    名义仓位上限/每张名义价值,
    交易所最大张数
))
```

不足最小张数则不开仓，不向上取整。杠杆只影响保证金限制，不把风险张数再乘杠杆。
该函数只接受已核实每张基础币数量的线性 USDT 合约，不能套用于币本位反向合约。
后续接欧易时根据 `ctVal`、`ctMult`、`ctValCcy`、合约类型验证换算，
读取最新 `lotSz/minSz/tickSz` 及订单类型对应的最大数量，再调用风险函数。
实盘还必须检查持仓档位、维持保证金、强平距离、盘口深度和市场价格限制。

## 7. 欧易模拟盘执行协议（待实现）

采用 REST 提交与查询，私有 WebSocket 获取订单/持仓更新；启动及断线恢复均用 REST 补查。
模拟盘与实盘使用不同密钥、运行实例和数据命名空间；模拟盘请求须带
`x-simulated-trading: 1`，运行模式不能只靠前端按钮改变。[欧易接口文档](https://app.okx.com/docs-v5/zh/)

第一版执行模式计划为逐仓、单向持仓，启动读取并核对账户模式。
进场意图以可接受最差价格约束，过期撤单；每次成交按实际张数维护交易所止损。
接口请求返回成功只是受理，不能据此增加持仓或宣布保护生效。

```text
意图：proposed → risk_rejected / approved → submitting
订单：submitting → live / partially_filled / filled / rejected / unknown
撤单：live / partially_filled → cancel_pending → canceled / filled
持仓保护：unprotected → attaching → protected / protection_failed
```

`unknown` 是本地无法确认结果，并非交易所终态。超时后按 clOrdId 查询，保留意图与风险预留，
不盲目重试。订单状态以累计成交量及交易所事件核对，处理重复与乱序，不能由旧 live 覆盖 filled。
clOrdId 在本地永久唯一；欧易只对未完成订单检查唯一性，不能代替本地永久去重。
[欧易订单管理指南](https://www.okx.com/docs-v5/trick_en/)

部分成交后立即保护已成交部分；附带保护单的生效时机要核实，不能等待整个入场单成交后才考虑止损。
保护失败时取消未成交入场数量，尝试只减仓退出，并冻结新单、保留风险预留、提示人工处理。
断网期间不承诺能够平仓；交易所托管保护单是关键保障。选择触发价格类型后需与回测模型一致。
单向持仓平仓使用适用的只减仓语义，防止平仓反向开仓。

单执行器使用 MySQL 会话锁；数据库/锁连接丢失后停止提交任何新单。
接管者先核对订单、仓位、保护单和风险预留，再恢复运行。仅一个锁仍不能消除网络请求在途的不确定性，
必须结合持久化意图与查询确认。Redis 不承担这部分正确性。

API 密钥只保存在后端环境或密钥管理服务，不写入网页、日志和 Git。
正式持续运行部署在可稳定连接欧易的常驻服务器，不能依赖会休眠的个人电脑。

## 9. 开发阶段及验收

1. **当前研究基础**：离线 demo 可运行；没有未来数据混入；缺失数据拒绝；
   可查询第一观察/锁定时刻；策略每个拒绝原因可追溯；风险张数不超过预算；数据库事件原子提交。
2. **真实行情与收益回测**：历史下载、不可变数据集、撮合/退出、资金费、样本外报告；
   必须可追溯每笔真实时序，不用少量样本或合成数据宣布盈利。
3. **模拟盘**：提供专用 MySQL 后跑集成测试；随后接模拟密钥。
   测试部分成交、撤单竞态、下单超时、WS 重连、数据库断开、进程重启、保护失败和熔断。
4. **小资金实盘**：策略统计表现和模拟盘订单闭环均通过后再实施。

MySQL 账号当前需专用库的 CREATE、SELECT、INSERT、UPDATE 及迁移锁使用权限；
后续增加 ALTER/INDEX 等迁移时另行配置。运行账号和迁移账号可在部署阶段分开。
远程库连接支持 `ssl_ca` 并验证服务器身份；连接配置基于
[PyMySQL 官方连接参数](https://pymysql.readthedocs.io/en/latest/modules/connections.html)。
